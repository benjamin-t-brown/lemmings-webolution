# Application icon

Playtest 25 Q8 asks for the supplied yay icon in the browser tab and on Windows. The page used an empty data-URL favicon. The Windows build had a version resource, and `SdlWindow::ensure` created its window without assigning an icon. This is a clone addition. Just Climb (`MM_CLIMB_002`) is the follow-up level for checking the icon through the connected session. [Ledger](../playtest/2026-11-21-playtest-25.md)

The source PNG is byte-identical to `build/icon/exe-icon-32x32-32bit-yay.png`. The standard-library generator uses a 2×2 alpha-weighted box filter at 16 pixels, preserves the 32-pixel RGBA frame and uses nearest-neighbour at 64, 128 and 256 pixels. The ICO stores 32-bit DIB frames with transparency masks. The export scanner requires the exact path and SHA-256 for both assets. [Frame and hash log](../../build/app-icon-001/pe-and-frames.log)

CMake adds `webolution.rc` only to the Windows game executable. In the first implementation, a game-target macro guarded the icon call inside inline `SdlWindow::ensure`. `FrontendWindow.cpp` compiled that call out and usually created the shared window first. The revised Windows executable passes `setWindowsWindowIcon` to the shared `SdlWindow` in `runApplication`. Both the frontend and gameplay use one `ensure` definition. When the frontend's `runFrontendWindow` first creates the window, `ensure` calls the configured setter before `SDL_ShowWindow`. The setter reads the embedded 32-pixel frame and calls `SDL_SetWindowIcon`. Gameplay reuses the shared window. The Wasm build copies the source PNG to `favicon.png` with a link dependency. The HTML links it relatively, the server serves it as `image/png`, and Pages stages it beside `index.html`.
