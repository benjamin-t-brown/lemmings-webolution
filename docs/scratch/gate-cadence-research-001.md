## 1. Answers to the three scoped edges

### 1.1 `[0x4E33BB]` (`this+0x1C9B3`, `this = 0x4C6A08`) and the forced-100 ms branch
* **Absolute-address references: exactly one, a WRITE of 0** at `0x45074E` (`MOV byte [0x4E33BB],0`) inside `0x450696`, the program entry routine, which zeroes nine adjacent flag bytes (`0x4E33B8-BF`, `0x4E3582-83`) and then calls the frame loop `0x45CFF9` itself (XREF + ASM + DECOMP). So the byte is **0 at process start**.
* **Reads:** the frame loop `0x45CFF9` only (DECOMP): the 100 ms clamp (`dt_ms > 100.0 || flag`) and the slow-frame counter reset. A set flag means: dt_ms = 100 every frame, one update per pass, slow-frame hint disabled.
* **Remaining unproved edge (named):** a byte scan (GREP) finds one `MOV byte [reg+0x1C9B3], imm8` store form in the image. The tool returns line counts, not addresses, so the store's address and the condition that executes it were **not recovered**. Consequence for implementation: if it were set during ordinary play, every frame would have dt = 0.1 s exactly (the same value as the stall cap). That cannot enlarge the per-update dt beyond the already-bounded 0.1 s, so the overshoot/row analysis of lever-timing section 5 holds either way. Nothing resolved links the byte to MM_W_012, to the gate/lever objects or to a user control. **Conclusion for MM_W_012 ordinary play: the byte is 0 (initial state), the forced branch is not taken, and the clamp only fires for frames longer than 100 ms. Not proved: that no later code sets it.**
* Corrects lever-timing section R item 1 (writers untraced): the startup zeroing and the single read site are now established; one store remains unlocated.

**Installed MM_W_012 record evidence (what can and cannot be parsed).** The record loader's input is **not** the compiled-level stream: `0x45C9AB` parses `Compiled\<level>.lvl` through its own local stream (`0x4432C1`), while `0x45651E` builds `demo\record\AA<level>.dPC` (`"%s\%s\%s%s.%s"` with `"demo"`, `"record"`, `"AA"`, the level name, `"dPC"`) into a different stream object at `this_demo+0x18` (`this_demo = 0x4C6A08 + 0x1C9B8 = 0x4E33C0`). I searched the raw name blocks of both installed archives and the filesystem (static trace section W, GREP/GLOB): neither `lemmings.box` nor `patch.box` has a `DEMO\`, `RECORD` or `*.DPC` entry (only `TEXTURES\MODELS\DEMOLBALL\*` texture names and UI strings), and no `demo` folder or `.dPC` file exists beside the EXE. So for MM_W_012 the record count is not "zero parsed from a stream"; **the stream does not exist**, and when `0x47E40D` fails with `param_2 = 0` it returns without a dialog and `0x456733` reads nothing. The byte layout (`u32 A`, `u32 N`, N x {`u32 type, u32 time_ms, u32 p2, u32 p3, f64, 24-byte sub-object`}, then `u32 S` + 0x50-byte sample records) is a static decode of the *code*, labelled as such; there are no MM_W_012 count/record offsets to report because there is nothing to parse. Absence is established from the archive directory bytes, the disk listing and the loader's own lookup order, not assumed; I did not run the clone's `Box` parser for this (see section 6; a future implementation task should assert it with `AssetLibrary::names()`).
Same reasoning for the second replay consumer `0x4567EF(this_demo, level_clock)`: it runs after every world update but is gated on `[this+0x14D] != 0 && [this+8] == 1`, so it is a no-op in ordinary play.

* **Therefore ordinary MM_W_012 play has exactly one proven event source: the 1 Hz level-clock event.** (The earlier "four unresolved run-time inserts" are now reduced to two with unresolved triggers, `0x413DF9` and `0x41527B`, neither of which writes a lever, gate or mask.) The frame loop splits dt at each boundary. Sequence (DECOMP `0x45CFF9`, per pass): `local_4c = head.time - level_clock; while (local_4c <= local_40) { level_clock += local_4c; local_40 -= local_4c; update(local_4c/1000.0); fire due events; 0x4567EF; reload local_4c }; level_clock += local_40; update(local_40/1000.0); fire due events; 0x4567EF; local_40 = dt_ms`.
  * Gate dt per update is `segment_ms / 1000.0`; the segments of one pass sum to `dt_ms`, so the *sum* of gate dt is unchanged, the *number* of world updates per pass is 1 + (events crossed). `dt_ms <= 100` after the clamp, so at most one 1 Hz boundary is crossed per pass.
  * A boundary that falls exactly at the end of the pass produces `update(local_4c)` and then a trailing `update(0.0)`. **Correction to attempt 1:** a *leading* `update(0.0)` ("boundary exactly at the current clock") cannot arise from the 1 Hz event alone: each firing runs at `late = 0` (the loop advances the clock exactly to `head.time`) and re-arms at `time + 1000`, so at the start of the next pass `head.time - clock >= 1`. It could only arise from a zero-delay run-time insert (`0x413DF9` with `x = 0`), which is one of the two unresolved triggers.
  * Under fast-forward each of the 7 passes runs this loop with the same `dt_ms`, so the level clock advances 7*dt_ms per frame and the event can fire in any of the passes (the pass that crosses 1000k ms gets two updates).
  * **Level-clock reset (answered):** `0x444D1E` writes `DAT_004CBF88 = 0` on every (re)load, immediately before inserting the fresh 1000 ms event. **Still not traced:** whether the previous level's list entries are cleared on reload (`0x45C95D`/`0x45C7E2` run before `0x45C9AB`). Consequence: only a stale entry with a different period could add split instants; none of the classified sources can write a lever/gate/mask, so the ordering contract is unaffected, but "split instants = frame + 1 Hz boundaries" is the proved minimum, not a proof of completeness.
* **Corrects lever-timing section 7 unresolved item 3 ("which timeline events MM_W_012 contains") and attempt 1 of this report:** the answer is "none from any installed file; the typed-record loader exists but is the gated Tutorial demo-replay path; one code-created 1 Hz countdown per level; two run-time insert sites with unresolved triggers that do not touch the gates". Attempt 1's statement that "the list is not filled from the level file / no per-level timeline records exist" is withdrawn as unsupported mechanism (the outcome for ordinary play is unchanged, now with provenance).

### 1.3 Zero-delta updates: paused / pre-start and ordinary `dt_ms = 0`
Two different sources give a `dt = 0.0` world update; both are full updates (DECOMP `0x45CFF9`):
* **(a) Ordinary 1 ms-resolution iteration (added in revision 2).** `dt_ms = timeGetTime() - previous` is an integer (`param_1[0x9719] = now - param_1[0x9718]`, then `param_1[0x9718] = now`). A loop iteration that starts in the same millisecond as the previous one gives `dt_ms = 0`. With the game running (`paused == 0`, `*this == 2`): `local_40 = 0`; the head event is at least 1 ms ahead (see 1.2), so the `while (local_4c <= local_40)` body is skipped and the trailing call runs `level_clock += 0; 0x4423D2(0.0); events(clock); 0x4567EF`. That is **one `update(0.0)` per pass** (seven under fast-forward), with the camera/title step also receiving `dVar1 = 0/1000.0 = 0.0`. Effect on the gate: no height progress; but the lever contact test, activation, request-word delivery and the request-1 settle/`armed`/`done` bookkeeping all execute exactly as in an update with dt > 0 (state-changing parts are dt-independent, section P of the lever-timing trace). Frequency in the original is not static knowledge (it depends on how fast the loop spins on the host); the clone must therefore define whether it ever issues dt = 0 updates, rather than assume they never occur.
* **(b) Paused / pre-start.** `0x45CFF9` calls `0x4423D2(this, 0.0)` on every loop iteration that reaches the update block when the paused byte `[this+0x55A0]` is set or `*this != 2`. It is a **full** world update, not a skip.
* **Height progress vs state change.** No height progress: ramp branches add `0.0 * rate`, the SET repaints the same rectangle, settle branches are dt-independent (lever-timing section P). But state *does* change: a request-1 gate's first update settles (`armed = 1, done = 1`) even at dt = 0.0; a lever contact in a dt = 0.0 update still activates (cooldown 0.0 installed) and writes `[+0xB8]`, the targets' `[+0x18C]` and the cooldown. Whether a stationary actor re-fires contact at dt = 0.0 depends on the **lemming** step at dt = 0.0, which is part of the parked lemming-motion work and was not traced (named edge). The lever's `+0xB8` alternation blocks a same-facing repeat.
* Frame-delta input around a pause: the previous-timestamp register is overwritten at the top of **every** iteration (including paused ones and iterations with the window inactive), so the first unpaused frame carries only that frame's own delta, not the paused duration.
* **Alternate caller `0x428A47` / x87 precision (materiality).** `0x428A47` calls the step with dt = 0.0 (height-neutral) and has no resolved caller; it matters only if it primes `armed/done` before the first loop update, which was not traced. x87: `dt*2.0` is exact; only `ms/1000.0` and `+ h` round, so precision control can move at most one ulp of `h`, and can move a row boundary by one update only if `h` lands exactly on an integer. Neither changes the integration boundary; retained as limitations (static-trace section V).

## 2. Production call path today (CLONE) and the mixed-cadence hazard

Today: `src/app/main.cpp:1029-1048` computes `elapsed` (float seconds, perf counter; overridable by `args.frames`/`runOptions.frameSeconds`) and calls `RuntimeSimState::advance(world, elapsed, ...)` at `main.cpp:1048` (`src/app/RuntimeHud.cpp:38-72`; pass loop `:48-70`): paused (`:40`) -> return false; `passes = fastForward_ ? 7 : 1` (`:46`); each pass `clock_.advance(elapsedSeconds)` (`:51`) then `while (... clock_.takeStep()) world.tick(...)` (`:52-55`); one tick = 0.2 s (`SimClock::stepSeconds`, cap 10 ticks per advance). `World::tick` (`src/sim/World.cpp:889-938`) has no dt argument (`tickDtSeconds() = 0.2`), runs release, then `step()` per lemming; lever contact is evaluated **inside** each lemming's `step()` (`World.cpp:843-851`, `leverAt` `:161`), toggling `Lever::state` only; no gate, no receiver step, no dt-ms integerization, no 100 ms clamp, no event split.

**Mixed-cadence hazard (analysis).** The original updates lemmings, lever contact and receivers in the same `0x4423D2(dt)` call, dozens of times per second, in the order lemmings -> levers -> receivers, with receivers seeing the contact-triggered request in the same update. If a per-frame gate step were added beside the 5 Hz tick:
1. **Activation instant.** Contact is evaluated at tick time only. The gate's request word is written at a tick; the original writes it in whichever frame the lemming reaches the trigger. The ramp start is therefore quantized to the tick and, independent of that, the lemming's arrival time is itself set by the parked lemming cadence. The first-raise rule (same-update dt) can be honoured only at frame granularity: the first gate step after the tick must use the dt of the frame that contained the tick.
2. **Mask visibility.** The original lemming step in update n+1 sees the mask painted by update n; between two clone ticks the gates would advance by up to ~12 frames while lemmings are frozen, so at tick t the lemming-visible mask can be ahead of the original-sampled one by at most `0.2 s * 2.0 = 0.4` rows (kind 0), i.e. at most one row boundary per tick. The only traced consumers of `0x200` are the fall-landing splat exemption and the terrain-probe rule (lever-links), so the effect is bounded, but nonzero.
3. **Within-tick ordering.** The clone evaluates a contact mid-lemming-loop, so lemmings later in the list in the same tick already see the toggled `Lever::state`; the original activates after the whole lemming list. Moving the gate step after the lemming loop preserves the receiver-after-lever order at tick granularity only.
4. **Fast-forward.** The clone repeats `clock_.advance(elapsed)` seven times; the original runs seven full updates, each with the full `dt_ms`. A gate-local step can reproduce the seven equal-dt gate updates; the lemmings still advance in 0.2 s quanta.
**Conclusion:** an isolated gate clock reproduces the gate's own recurrence for a given dt sequence and activation edge. It **cannot** reproduce the original lemming/lever/receiver ordering or the absolute activation instant. That would require stepping lemmings with the same variable `dt` and one update per frame (the parked D1/D3/base-clock work). Equal dt units alone do not imply ordering fidelity.

## 3. Implementable scope G1: gate-relative contract only (not queued; needs explicit authorization)

**What G1 claims:** given the request-word write and the frame's dt sequence, the gate follows the proven recurrence (compare-before-add, no clamp, SET each update, `armed/done` bookkeeping, mask rectangle `[ftol(min.x), ftol(max.x)) x [ftol(min.y), ftol(min.y+h))`) with the original's input policy: integer ms, 100 ms cap, 1 Hz level-clock splitting, seven equal-dt passes, dt = 0.0 while paused. **What G1 does not claim:** absolute activation time, lemming-visible intermediate masks, the within-update lever-contact order, fluid rendering, or full MM_W_012 fidelity.

Files and call sites (a future task, none changed now):
1. `src/app/RuntimeHud.h/.cpp` - `RuntimeSimState::advance` (`RuntimeHud.cpp:38-72`, pass loop `:48-70`): keep the existing pass loop and `SimClock`/`world.tick` calls byte-for-byte; after each pass's tick loop, call a new gate-input object once per pass (`GateInput` below), then `world.stepGates(dtSeconds)` once per returned segment. Paused: skip as today, or call `world.stepGates(0.0)` (ramp-neutral; see matrix). `togglePause`/`resume` already rebuild `clock_`; the new object resets its level counter only on reload, not on pause.
2. New small class `GateInput` (e.g. `src/app/GateInput.h/.cpp`): (a) integer ms: convert `elapsed` to integer ms with carried fractional remainder so the sum of integer dt equals real elapsed ms (the original gets exact integer deltas from `timeGetTime`); a frame whose integer result is 0 yields `dtMs = 0` and still runs one `stepGates(0.0)` per pass, as the original does (1.3a), rather than being skipped; (b) `dtMs = min(dtMs, 100)` using the original comparison (`100.0 < dt` clamps; exactly 100 unclamped); (c) `splitByEvents(dtMs)`: level counter `levelMs` (reset to 0 on every load, `0x444D1E`) and next boundary `1000k` -> returns the segment list `[boundary - levelMs, remainder]`, where a boundary landing exactly on the frame end yields the first segment of full length and a trailing zero-length segment (no leading zero-length segment arises from the 1 Hz event alone, 1.2); (d) seven passes reuse the same `dtMs`. The two unresolved-trigger inserts (`0x413DF9`, `0x41527B`) are **not** modelled and the result must say so. This is the smallest new input policy; it does **not** replace `SimClock`.
3. `src/sim/World.h/.cpp` - `FluidGate` records, `World::stepGates(double dt)` (line-for-line section 3 of lever-timing: raise only; lower branch for the load settle and reload), called **after** `tick()`'s lemming loop is complete and only from `RuntimeSimState::advance`, never inside `World::tick` (so `tick()` and lemming timing remain unchanged); lever activation writes the request word at the existing contact site (`World.cpp:843-851`, after adding link lists/cooldown from `entities_42acac`/`tagged_entities`, which `lemmings::read_compiled_level` already parses).
4. `src/sim/RetailLevel.cpp/.h`, `src/sim/Terrain.h/.cpp` - the load pass (request 1 -> clear 192 cells per gate, 3600 -> 528) and a rectangle SET/CLEAR with the original traversal (`x & 0xFF`, y clamp, Y flip `destY = height - 1 - y`), as in lever-timing section 7.
5. Reload: `loadRetailLevel` rebuilds `LevelSetup`; `GateInput` level counter returns to 0 at the same point (DECOMP: `0x444D1E` writes `DAT_004CBF88 = 0` and re-inserts the 1000 ms event on every load; the frame loop also overwrites the previous-timestamp register after `0x45C9AB`, so the load duration is not charged to the first frame). Whether stale list entries survive a reload is untraced (1.2) and does not affect the gates.

**Smallest park reopening required:** only the *elapsed-input policy* item of the base-clock park - adding a gate-local ms/100 ms-cap/1 Hz-split input beside `SimClock`. It leaves the 0.2 s tick quantum, lemming positions/contact order, release/digger timing, D1/D3 and Armageddon parked. It requires an explicit user decision because it creates a second time base in the clone, and the report must label results "gate-relative". If the user instead wants ordering fidelity, the smallest broader prerequisite is the parked work itself: a variable-dt per-frame update that steps lemmings, lever contact and receivers in one call with the same dt (D1/D3/base-clock); no intermediate option provides that claim.

**Actual-level acceptance (MM_W_012 through `loadRetailLevel`, source-built, registered in CTest):** counts from an independent transcription of the x87 operation order (do not hand-round decimals); lever (183,60) with the synthetic walker injection labelled as a fixture, not natural play; no `0.2`-second tick constant in the gate path; assertions below.
