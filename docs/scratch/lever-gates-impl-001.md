## 2. Semantics implemented, and what is bounded

STATIC sources: lever-links sections 1-3, lever-init proof chains 1-2, lever-timing section 3, gate-cadence section 1.

* **IDs.** A message resolves through `LevelSetup::objectIds[id]`, filled in the loader's collection order (0x448650, 0x448710, 0x4487F0, 0x4488F0, 0x4489F0, 0x448AF0, 0x448BD0, 0x448CB0, 0x448D90, 0x448E70, tagged, named); a later construction wins. A gate is addressed by its **serialized base id**, never by its position: in MM_W_012 id 5 is stream index 12 and id 6 is index 11, and the test asserts both facts (`index != id`).
* **Message types.** Type 4 -> `request := 0` (raise), type 5 -> `request := 1` (drain), only on a `ObjectClass::Gate` target. Type 0, unknown types, negative ids (the `-2` special arm), non-gate targets (levers and every other collection) and empty slots are counted in `leverStats` and change nothing. Nothing is mapped to a gate by position, class guess or coordinates.
* **Lever activation.** `activateLeverFace`: face +1 -> `state := 1`, list +0xCC; face -1 -> `state := -1`, list +0xBC; other faces do nothing. The existing facing/state filter, cooldown and "first accepted lemming per lever per update" rules are unchanged; the cooldown is now loaded from the record (`double [+0x98]`, installed 0.0).
* **Load.** Reader pass per receiver in stream order: request 1 -> `h := low`, CLEAR the stream AABB; otherwise `h := high`, SET it (`[+0x68]` is not recomputed). Ctor values `done = 2`, `armed = false`. Then the load-time fan-out of each linked lever's stored face list (all four MM_W_012 stored-face lists are empty, so nothing is sent at load there).
* **Step** (`FluidGate::step`, every update, after the lever contacts): if `request == done` return; request 0: `if (h < high) h = dt*rate + h; else { h = high; if (armed) { armed = 0; done = 0 } }`, then `maxY = minY + h` and SET; request 1: `if (h <= low) { h = low; if (!armed) { armed = 1; done = 1 } } else { CLEAR current AABB; h = h - dt*rate; maxY = minY + h; if (low < h) SET }`. Compare-before-add, no clamp, overshoot rows never cleared, settle repaints on the raise side and does not on the drain side, exactly the accepted transcription. Rate: kind 0 = 2.0, kind 1 = 0.5 (table `0x4BF6F8 + kind*0x48`); any other kind has no traced rate and does not ramp.
* **Bounded, not approximated.** (a) Kind 1 (`0x2000`) receivers keep full request/height/armed/done state but paint nothing: the clone has no `0x2000` plane and MM_W_012 has none (0 stored `0x2000` cells, all 19 receivers kind 0). (b) The `+0x12C` list dispatched at drain-settle is empty for serialized objects and is not modelled. (c) Wave phase, child models, emitters and the `0x4CBB08` secondary objects of the step tail are untraced and absent. (d) A request word other than 0/1 is treated as "not 0" (drain), which is not traced; the installed values are 0/1. (e) Other levels: the same code runs for every installed level that has `entities_42acac` or tagged type-1 records; only MM_W_012 was measured by this task.

## 5. Limits and newly exposed differences (reported, not repaired)

* **Hybrid timing is unchanged and still the limit.** Gate steps use the accepted shared per-update dt; walkers/fallers are continuous, other lemming states still run at 5 Hz boundaries. The synthetic activation instants depend on that. D1/D3, release/digger, Armageddon and the other parks were not touched.
* **Legacy `World::tick()` does not step gates or dispatch lever messages.** It remains the fixed-tick compatibility wrapper (no dt contract). The connected app uses the explicit path. A caller that still drives `tick()` on a loaded retail level now sees the drained mask after load and never a refill. No production caller does.
* **Stored initial face is not applied to `Lever::state` (exposed difference).** The original applies `[+0xDC]` through `0x00436E6A` at load. For lever (183,60) that face is +1, which equals the clone's loaded state, so the task's lever is exact. Levers (79,60) and (189,35) store -1, and the clone still loads their `state` as 1. Applying it would flip `levers[0].state` to -1 and break the unchanged assertion `test_sharedtiming_baseline.cpp:185` (`reloaded.setup().levers[0].state == 1`), so it was **not** applied and no assertion was edited. Consequence: the first pull of those two levers uses the wrong facing. Their stored-face list *is* fanned out at load (empty here). This needs an explicit decision to update that existing assertion.
* **Unmeasured consumers.** The mask change reaches only the existing consumers of the clone's `zoneWater` plane (fall-landing splat exemption, hazard predicates used by the survey tests). It is not visible fluid, an emitter, new drowning logic or complete gate fidelity; the moving surface, wave phase and child models are untraced and absent.
* **Other levels** that carry receivers or tagged type-1 records now load with their receivers applied; their terrain `zoneWater` counts change accordingly (baseline-style surveys such as `playablebaseline` print hazard-cell counts). Only MM_W_012 was checked for the installed-data numbers here.
* **Natural play.** All activation scenarios place a walker; no claim of a natural lever route or win is made.
