# Installed resource lifecycle integration

This is a source integration check using the user's installed archives. It is
distinct from static reading, offline native instruction comparison and a live
game session. It introduces no additional claim about original routine bytes.
Each recovered component links its own exact executable identity and byte pins.

`tools/lemmings_resources.cpp` composes the recovered [manager constructors](resource_manager_construction.md),
[slot registration](resource_registration.md), [acquire/release](resource_cache.md),
[list search](resource_cache_find.md), [loading/name dispatch](resource_cache_load.md),
[sprite factory](sprite_factory.md), [sprite parser](sprite_resource.md),
[runtime sprite reader](sprite_runtime_read.md), [texture ID resolution](sprite_piece_runtime.md),
[nested destruction](sprite_resource_destruction.md), [file stream core](file_stream_runtime.md),
[open finalization](file_stream_runtime_open.md), [rectangle geometry](sprite_render_geometry.md),
[animation playback](animation_playback.md), and [cache cleanup](resource_cache_cleanup.md).

## Adapter boundaries

The harness owns host allocations and uses the recovered `.box` index and
patch-first lookup to supply file bytes in place. File construction, block read,
close and destruction use the recovered stream core with an explicit memory
backend. Original open selection, retry and drive discovery in `47E40D` remain
outside this adapter. A fatal open diagnostic is translated by the tool's
termination adapter into a command failure; the original factory's exit status
is zero.

The read callback builds actual runtime clip/frame/piece/triple arrays through
the recovered reader. The portable allocator reserves aligned host elements,
with the original four-byte cookie immediately before array elements. A map
translates the cookie address passed to the original free boundary back to the
owning host allocation. The recovered nested destruction routines perform all
array traversal and clear operations. No texture release is added: the original
piece destructor is empty.

The existing serialized parser also decodes the same bytes into independent
vectors. The harness compares the serialized values represented by runtime
fields against those vectors,
including clip names, speed, frame/piece counts, integer words, doubles and
triple data. Runtime signaling NaNs are compared after original x87 quieting.
Piece `+44` must retain the allocator's `A5A5A5A5` pattern. Every piece's signed
texture ID must resolve to the exact serialized name in the recovered texture
registration table. Animation metadata is projected from the independent
vectors. Host pointer sizes are adapted; this asserts no x64 binary ABI match
and invokes no original rendering code. Before invoking the runtime reader,
the tool rejects decoded texture names of 128 bytes or more: the serialized
field can hold longer names, but the recovered registration routine requires
the name and its NUL to fit a 128-byte slot. This tool-level diagnostic preserves
the recovered routine's original input precondition rather than adding bounds
checks to that routine.

The command builds no display, loads no texture pixels and executes no original
game process. Animation binding and advancement use recovered source routines
with the parsed clip metadata. Rectangle geometry consumes the runtime arrays
for every piece, using chosen harness position/size inputs and the normal scale
branch. Its final renderer callback checks finite positions and valid texture
IDs and counts submitted quads. This is not a recovered gameplay camera or pose,
nor a rendered-frame comparison.

## Installed fixture

`tools/check_installed_resource_lifecycle.py` independently reads the archive
entries and decodes their counts using the existing Python sprite checker. It
compares that inventory with the harness output. The installed fixture contains
19 sprites, 132 clips, 1,526 frames, 7,354 pieces and 167 unique texture names.
Every sprite has a usable animation clip in this fixture.

`tools/check_resource_lifecycle_boundaries.py` also generates two synthetic
one-sprite BOX fixtures in a temporary build directory. A 127-byte texture name
completes the full load/unload/recreate lifecycle; a 128-byte name is rejected
with a diagnostic before entering runtime registration. This boundary regression
passes on x64 and x86, and the installed 19-sprite check passes after the guard.
These generated bytes contain no original game assets and are removed afterward.

For each registered resource, the harness acquires it twice, checks stable
identity without another creation, binds/selects/advances animation, and releases
all references. It then retains one resource while invalidating and unloading:
zero-reference nodes are evicted; the retained node survives with a null resource.
Recreation repopulates that node and refreshes entry caches. It releases and
evicts the retained node, then performs another acquisition after eviction.
All 7,354 pieces generate rectangle geometry. All 21 created factory objects
are destroyed, with 21 archive-finalization seeks, 21 block reads and 21 actual
file closes. Loaded count, node storage, sprite storage, every nested runtime
allocation and file objects end empty. Finally it clears unused entry flags,
checks preservation of their upper unknown bytes, and reuses the first slot
without increasing the slot count.

With `LEMMINGS_ARCHIVE` configured, CTest runs this as
`installed_resource_lifecycle` on both x64 and x86. The archives stay outside the
repository. To run manually:

```powershell
build/lemmings_resources.exe --archive 'C:/progs/Lemmings Revolution/lemmings.box' --patch 'C:/progs/Lemmings Revolution/patch.box' --all
```

Use `--sprite LemmingsLo` to exercise one resource. The JSON output reports
decoded counts, creations/destructions, animation checks, final loaded count
and slot reuse. Original gameplay integration and rendered frame comparison
remain pending.
