# OpenGL renderer conversion plan

**Keep the software renderer as the reference and ship the GPU renderer as an opt-in backend first.** Target OpenGL 3.3 core on Windows and WebGL2/GLES3 in the desktop browser. Start at the existing 640×480 logical play resolution. Compare both renderers on the same prepared frame before changing clipping or choosing a new default. This plan is the only work pulled forward. Every implementation phase below waits for playable v1 and user approval. [Roadmap](../agent/IMPLEMENTATION_PLAN.md) · [Post-1.0 scope](POST_1_0.md)

- **Clipping.** Playtest 7 W1 reports minor z clipping during a twelve-level session, without naming the offending level, object or camera pose. Playtest 9 Y9 reopened W1 with side-on bashers. Y10/Y11 identified the Loggerheads wall turn and builder bridge feet. Those cases subsequently received software fixes. Use them as regressions, then identify any remaining artifact at a specific pose before changing clipping or depth. Playtest 11 A4 separately describes a falling lemming clipping near a surface, also seen by the user in the original. That is an optional visual improvement. [W1](playtest/2026-11-15-playtest-7.md) · [Y9–Y11 repair](scratch/basher-occlusion-001.md) · [A4](playtest/2026-11-16-playtest-11.md)
- **Frame time.** The optimized software path already averaged 6.401 ms on native Kriss Kross rotation. Its p95 was 7.279 ms against a 6.944 ms refresh budget. Browser playtest 16 F3 reported jerky entry turns, slow right-drag and music breaks. The later pthread measurements covered Wasm scene rendering in Node. The decision needs tail latency on Windows and actual presented browser frames with sound. [Native measurements](scratch/frame-rate-144-001.md) · [F3/F4](playtest/2026-11-18-playtest-16.md) · [Web measurements](scratch/web-perf-001.md)
- **Gameplay depends on the picture.** Hatch picking reconstructs the visible hatch rectangle from completed scenery depth. Zoom samples the actor or scene under the pointer. A fast GPU frame that hands input stale depth can change what the player can do. Promoted recordings play back the already resolved commands. The visual comparison and interactive checks below cover that gap. [Application loop](../src/app/main.cpp) · [Hatch queries](../src/app/BackdropScene.cpp) · [Replay contract](../src/app/Replay.hpp)

**Software raster contracts.** `Raster` owns tightly packed, top-down RGB, a binary64 scene Z per pixel cleared to positive infinity, and a separate `ActorDepth`. Both triangle paths use pixel centres and affine screen-space comparison Z. UV interpolation uses reciprocal homogeneous W (RHW). Tube sampling wraps the four bilinear taps about `uv * size − 0.5`. `rasterizeSceneTriangle` additionally supports point/linear, wrap/clamp, flat vertex-zero or perspective Gouraud diffuse, selected/modulated alpha, alpha reference, blend factors and explicit depth comparison/write. Its inclusive edges can shade a shared edge twice. Scene byte conversion rounds to nearest. Diagnostic observers receive ordered RGBA write events. [Raster](../src/app/Raster.cpp) · [SceneRaster contract](../src/app/SceneRaster.h) · [SceneRaster implementation](../src/app/SceneRaster.cpp)

`RasterCommandBatch::add/flush` bins validated draws by clipped Y extent into eight-row bands, preserving submission order inside each band. `RasterRows::run` distributes disjoint rows to the caller and workers, then joins at a barrier before count/error reduction. The cap is **16 participants on native, eight on Wasm**, including the caller. Extreme sampler inputs preserve eight error ranges. Observer paths draw synchronously. Those jobs are the software implementation of ordering and memory ownership. The GPU can submit ordered draw ranges on one context thread. [RasterRows](../src/app/RasterRows.h)

**Depth and clipping.** `adaptPackedSceneMeshVertex` calls `packSceneVertex`. Scaled view Z minus source bias is stored as float, RHW uses `0.25f / storedZ`, and comparison Z is decoded to view units. Billboard RHW uses the native slot Z while comparison Z divides that slot by the diagonal projection/source/projection coefficient. Tube RHW is `1 / viewZ` before the comparison offset. A stock perspective projection changes which fragment wins. Also, `TubeScene` can reject a whole quad if a corner fails `project`, and backdrop mesh fans reject a triangle containing non-positive view Z. `clipScenePolygon` models near and screen clipping in isolation and has a smoke unit test. Its callers in this checkout are tests. ## Renderer boundary

Create the boundary **between preparing a draw and writing its first pixel**. The application continues to own simulation, elapsed time, camera, animation, picking rules, audio and progress. A prepared frame holds the logical viewport, camera, pass order and draws. Each draw carries geometry or sprite placement, a leg-owned asset handle, UV/RHW, comparison Z, diffuse colour, material state and any stable actor/source ID it needs. HUD layout contributes screen-space draws. Extract this incrementally at `TubeScene::render`, `BackdropScene::renderStage` and the actor/2D compositors. Keep each representation close to its existing producer.

- **One preparation, two consumers.** Select animation, first-draw RNG, gate state, terrain revisions, actor order and UI state once. Resolve hover against the scene before issuing the dependent overlay draws. Let either backend consume the same resolved draws. In comparison mode, use a single application update, check each backend's query results independently and present one frame. A redraw or a second backend must never advance the world, age a particle, consume another random value or play another cue.
- **Software.** Implement the draw interface with the existing `Raster`, `rasterizeSceneTriangle` and compositors. Preserve their ordered diagnostic callbacks, caches, PNGs and SDL dummy/headless operation. This is the executable reference throughout migration. Keep software as the default until the final decision. Proposed startup selector `--renderer software|gl|auto` should still enter the ordinary frontend when given alone. Provide the browser equivalent at Start. Log the requested and actual backend once. An explicit GL comparison requires a real GL result. Interactive `auto` may fall back to software.
- **GPU resources and portability.** Use SDL2 and the Windows system `opengl32` library with the registered MinGW toolchain. The active game currently links SDL2. Add the GL linkage to the native backend target when implementing it. Set SDL core profile 3.3 and context attributes before creating an `SDL_WINDOW_OPENGL` window, load newer entry points via `SDL_GL_GetProcAddress`, verify the actual version and framebuffer, and swap with `SDL_GL_SwapWindow`. Give the GPU presenter exclusive ownership of this window/context. On Emscripten enable WebGL2 in the link settings (e.g. `-sMAX_WEBGL_VERSION=2`), request an ES 3.0 context and confirm the returned version. Check that software can still present when WebGL2 creation fails, including browsers that require a fresh canvas to switch context type. Keep one shader body per operation with a generated `#version 330 core` or `#version 300 es` preamble and ES precision declarations. Use the common vertex/fragment, indexed-buffer, texture and FBO feature set. [Windows build rules](../.claude/rules/windows-msys2-build.md) · [Current target linkage](../cmake/webolution_app.cmake)
- **Lifetime.** Keep immutable decoded assets available to rebuild GPU textures after a context change. Scope uploads to the archive generation and GL context, mesh buffers to the level, dirty ranges to terrain/gadget revisions, and offscreen framebuffer objects (FBOs) to the render size. On failed initialization, clean up partial resources before starting the software presenter. On browser context loss, suspend submissions, keep the session/save lock, and recreate resources from CPU data or present the next frame through software. Preserve the selected level, input focus and pause state on recovery.
- **Frame queries.** Return a token for the displayed camera and world presentation state. Expose actor placement boxes, visible hatch bounds, point depth for zoom, and an on-demand composed image. The production overload of `injectedWalkerScreenBoxes` calls `prepareInjectedWalker` without a clipped-sprite target, so placement boxes do not encode final opaque ownership. Keep its submission/placement and nearest-box pick policy on CPU. `hatchHoverTargets` actually compares mesh-pixel Z to the completed scene with a 0.5 world-unit tolerance. Compute those extents from the same depth comparison, for example with a GPU mask followed by a reduction to the minimum and maximum visible coordinates for each candidate hatch. An ID sampled only under the cursor loses the rectangle behavior. For zoom, retrieve the actor depth if finite, then the scene sample. Keep a completed token through event dispatch, materialize it on demand, and use a small synchronous query when a click needs it. Measure stalls before enabling GL for interactive play. [Displayed input consumers](../src/app/main.cpp) · [Placement](../src/app/TubeScene.cpp) · [Hatch bounds](../src/app/BackdropScene.cpp)

### GPU contracts to settle first

1. **Comparison depth.** Start with CPU-projected vertices and the clone's submit/reject decisions. A portable shader can set clip W to 1, interpolate `q = RHW`, `uv*q` and `diffuse*q` affinely, then divide by `q` for perspective attributes. Pass preselected flat colour for a flat face. Interpolate the separate comparison Z affinely and map it monotonically into a common depth interval. Choose and log the interval from the submitted scene, including bias and actor/effect extents. Reserve a clear value for infinity, detect out-of-range values, and measure depth resolution near coplanar surfaces. This avoids depending on desktop-only interpolation qualifiers. Finite depth precision and hardware edge ownership can still differ from binary64 and inclusive CPU edges.
2. **Depth reads across passes.** Start with a single-sample RGBA8 colour target and sampleable scene depth. Preserve distinct pipe-only accepted depths, pre-water scenery and completed depth when needed. Recreate the drowning snapshot by substituting completed depth only where it differs from the immediate post-fluid value, including secondary geometry and counter gates. Composite actors into the scene colour while testing a separate actor-depth target and stable owner. Use separate passes/textures whenever a shader reads a previous attachment. Check framebuffer completeness on both targets. For portable depth/owner diagnostics, encode samples to a readable colour attachment with explicit range, sentinel and precision. Floating-point colour attachments and desktop depth readback must have a portable alternative.
3. **Actor intersections.** Evaluate the upright plane at logical fragment centres, test the edited collision footprint using cylinder ring data and an integer grid texture, and keep body, brick and decal depth policies independent. Reuse the CPU plane coefficients and cylinder interpolation initially. Give actor depth and owner an explicit tie policy and check same-depth overlaps including particles submitted after actors. Sorting the sprites by centre alone cannot resolve a nearer brick corner. If quantization changes the winner, compare with the CPU owner/depth for that overlap and keep interactive play on software until the discrepancy is resolved. Keep expensive slow paths visible in timing results.
4. **Colour and blending.** Use linear byte-domain render targets with sRGB conversion, dithering, multisampling and mipmapping disabled for initial parity. Specify each sampler and alpha operation. Linear sampling combines RGBA before the alpha test on scene paths that request it. Actor texels need point lookup and frame-local clamp. Where `blendOptions` is used, selector 0 disables blending, 1 uses SRC_ALPHA/ONE_MINUS_SRC_ALPHA, 2 uses ONE/ONE and 3 uses SRC_ALPHA/ONE. Keep keyed cutouts distinct from the conditional caret billboard policy, which selects texture alpha and disables the alpha test. A transparent fragment there can still write depth. Validate integer rounding and alpha preservation in 2D with real decoded assets. If fixed-function blending misses required bytes, sample a separate copy of the destination for the affected ordered operation or cache the exact CPU-composed static panel.
5. **W1 diagnosis and improvement.** Keep view-space inputs available before CPU rejection. At the reported pose, compare pass coverage, depth winner, owner and colour while rotating through it. For a near-plane loss, clip crossing geometry in homogeneous/view space before division, retaining corner attributes and winding. For a depth tie or actor footprint error, fix the measured comparison or proxy instead. Verify nearby surfaces, rear-side hatches, wall contacts and bridge feet through a full turn. A matched software defect is a parity success and a separate visual defect. Record any approved deviation with level, pose and material. W1 remains open for identification if nobody can reproduce it.

## How to decide parity

Use the same executable, the same installed archives and the same in-memory frame. Compare top-down logical pixels **before** presentation scaling. Keep the CPU result, GPU result, heatmap and per-pass counts in the future task's `build/` directory. Record level, camera, viewport, phase/clock, backend/driver, pass, material and frame number. In comparison mode read the offscreen GL colour via `glReadPixels` only at requested checkpoints, flip row order once, and define alpha and pack alignment explicitly. For depth and owner, use a diagnostic pass into colour and decode on the CPU. Count the cost of readback separately. Disable comparison and forced synchronization during throughput measurements.

| Compared quantity | Proposed acceptance rule |
| --- | --- |
| Static decoded texture, opaque UI blit, glyph/SPR source texel, transparency/alpha-test mask, logical placement, map selection and query result | Exact bytes or exact IDs/rectangles for the defined operation and identical inputs. Compare opaque geometry coverage separately from filtered colour. |
| Linear-filtered or blended 3D surface interior | Start with at most one 8-bit value of error per channel per pixel. Report maximum, histogram and affected pixel count for each pass. Larger or systematic differences require a trace to the responsible material/rounding step. |
| Triangle boundaries, depth and actor overlap | Report mismatches even on shared edges. Review a one-logical-pixel edge band separately, with per-source competing depths, coverage and winner. Check finite/clear classification exactly and numeric depth against the chosen representation's quantization bound. Reject new holes, flicker, hidden or exposed actors and changed input decisions. Admit a W1 difference only at the documented, approved cause. A small full-frame average cannot excuse a missing lemming. |

These are proposed backend comparison rules. The existing smoke assertions and historical original-image gates keep their own criteria.

- **Which tests draw.** The smoke list includes `sceneraster`, `sceneclip`, `scenedepth`, `scenebillboardsource`, `actorsprite`, `mapscene`, `runtimehud` and `pausecaption`. The 17 sweep chunks cover 102 installed levels. `test_levelsweep.cpp::runChild/observe` enters a level directly, materializes settled and terminal frames, checks image statistics and produces thumbnails for the aggregate report. Keep the software smoke and recovery gate usable with dummy drivers. Run representative visual consumers on a real context before rollout and the existing sweep on GL for breadth. Record which backend actually rendered. ## Decisions for the user

1. **W1 and A4.** Which level, object and camera movement best reproduce W1? Start with the known side-on basher, Loggerheads turn and bridge-feet views. A description of any remaining case in ordinary play is enough to start. Should A4's fall-near-surface appearance be preserved, or improved as a separately approved deviation?
2. **Parity.** Are the proposed exact, one-byte and boundary-review rules acceptable? Which intentional visual differences, if any, may ship in the default mode?
3. **Performance and hardware.** Confirm the Windows reference GPU/display and preferred vsync setting. Which desktop browser, GPU and refresh rate should qualify for browser rotation? The 60 Hz browser target and tail thresholds above are proposals.
4. **Rollout and resolution.** After measured sign-off, should `auto` prefer GL on both platforms, or should GL remain opt-in on either? Should higher internal resolution receive its own task after 640×480 parity? Window enlargement already works today.

The lead can review the plan now. The next production decision is whether to authorize phase 1 after the playable-v1 milestone.
